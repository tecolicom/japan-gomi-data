# 新自治体 収録プレイブック

収録実績 (34 自治体・905 コース、2026-08-19 時点) を蒸留した、1 自治体を最短で収録するための手順書。
エージェント (または人) はこれと [`opendata-sources.md`](opendata-sources.md) を読んでから着手する。

**入り口が 2 つある。先にどちらか決める。**

- **新規収録** (まだデータが無い) — §0 から順に進む
- **既存収録の再構築** (データはあるが生成器が無い) — **§6 へ**。既存データが照合の基準になるので手順が違う

## 0. handle を引く (1 分)

自分で綴りを考えない。全国自治体レジストリ
[tecolicom/city-tecoli-data](https://github.com/tecolicom/city-tecoli-data) の `municipalities.yaml`
(lg.jp/WHOIS 検証済み 1,786 件) から `handle` / `code` / `yomi` を引く。
コードからは `tools/_lib/registry.mjs` の `lookupMunicipality()` が使える。
配置は `municipalities/<都道府県romaji>/<handle>/`。

## 1. ソース調査 (30 分で見切る)

**まず `municipalities/<県>/<handle>/survey.yaml` を見る** — triage 済みの自治体なら一次ソース URL・形式・粒度・
罠・運用ルールが既に書いてある (調査の大半を省略できる)。無い自治体は以下の手順で調査し、
結果を survey.yaml として書き残す (docs/triage/ の県別 YAML・CSV は `scripts/triage-csv.mjs` で再生成)。

**優先順に探す** (上ほど良い。見つかった時点で下は補助に回す):

1. **テキスト版カレンダー** — 視覚障害者向け等で市が配布する「日付・曜日・品目」列挙のテキスト。
   日付レベルで直接照合でき最良 (調布)。検索: `site:city.<x>.lg.jp カレンダー テキスト版`
2. **収集曜日のオープンデータ CSV** — 自治体 OD カタログ・都道府県カタログ (中野)。
   都カタログ等は CLI から 403 のことがある → リソース実体 (自治体ドメイン) の URL を検索で見つけて curl。
3. **公式サイト内の CSV/JSON** — 収集曜日検索ページを駆動するデータファイル (杉並の garbage.csv)。
   ページの HTML ソースから `.csv` `.json` への参照を grep する。
4. **公式 HTML 表** — 町名×種別の一覧表 (練馬・川崎)。
5. **PDF** — 実装方針は下の 1 コマンドで決まる。pdftotext の見た目で決めない。

`pdfplumber` で日程ページの要素を数える:

```python
p = pdfplumber.open(PDF).pages[N]
print(len(p.chars), len(p.lines), len(p.rects), len(p.curves))
```

| chars | 罫線 | 方針 | 実例 |
|---|---|---|---|
| >0 | あり | **まず `find_tables()`**。表が復元できれば実装はほぼ終わり | 日高 (7行×14列が一発で取れた) |
| >0 | 表にならない | 文字の座標で解く | 中野・上富良野 |
| **0** | あり | **色ベース抽出**。罫線でグリッドを復元し、セルの塗り色で品目を判定 | 飯能・秩父広域・青梅 |
| 0 | なし | 本当の画像 PDF。全数転記はせず §3 のサンプリングで扱う | — |

- **文字数だけで健全性を判断しない**: 隠し OCR 層 (杉戸) や CID フォント化け (瑞穂) は
  「テキスト層あり」に見えて実用不能 (実質画像 PDF)。
- **「pdftotext で曜日が取れない = 画像 PDF」と決めつけない** (青梅はこれで difficulty 4 と誤判定されていた)。
- テキスト層があっても**すべてが読めるとは限らない**。日高はコース番号 10 以降が黒丸に白抜きの数字で、
  1 文字の制御コード (`\x1a`) になりコードポイントが取れなかった。読めない要素は、読める要素との
  整合を検査したうえで補う (詳細は `tools/pdf-extractor/hidaka/README.md`)。
- **`chars` が多くても品目が取れるとは限らない。** 国分寺は 11,433 字あるが中身は日付・曜日・
  電話番号・注意書きで、品目名は「資源」「プラスチック」「本・雑誌」「有害」の 4 種だけ。
  **最も基本的な「もやせるごみ」は 0 件**で、袋や瓶のイラスト + アウトライン文字になっていた。
  文字数を見て「機械可読」と判断せず、**品目名で grep して件数を数える**。
  なお色ベース抽出も万能ではない。飯能はセル背景が品目ごとに 1 色だったが、
  国分寺のようにイラストだと色が品目間で重複する (緑の束が「本・雑誌」と「牛乳パック類」の両方)。

**町村で公式サイトに日程が無い場合、処理を担う一部事務組合のサイトを必ず確認する** (越生町の教訓:
町サイトは組合へ誘導するだけだが、組合サイトに町別カレンダー PDF が実在した。組合の PDF 命名は
`<town>2026_a.pdf` のような規則性があることが多い)。

同時に調べて記録するもの:
- **検証ソース** (一次と独立な第2表現): 地域別カレンダー PDF、冊子の一覧表、別レイアウトのカバー表 等
- **運用ルール**: 祝日・振替・お盆の収集有無 / 年末年始の休止日 (毎年 12 月告知型か、カレンダーに明示か)
  / 粗大ごみの扱い (申込制なら rules 対象外) / 集団回収 (区収集外の品目)
- **ライセンス**: OD なら CC BY 等を記録。通常ページなら「事実データの抽出」整理 (練馬先例) で可
- 地区割の単位 (町丁目 / 地区番号 / コース) と、丁目分割・区またぎ同名の有無
- **収録期間を何が裏付けるか。** ここは見落としやすい (2026-08-19 に東久留米で撤退の決め手になった)。
  日付入りカレンダーなら自明だが、**曜日規則だけのソースは自分では期間を主張しない**。
  その場合は「祝日の扱い」「年末年始の休止日」がどこまで公表されているかが実質の上限になる。
  東久留米は曜日規則の HTML も PDF も日付を持たず、祝日ページの掲載が 4/29〜9/23 で
  「上記以降の祝休日につきましては、決まり次第掲載します」と明記されていたため、
  裏付けのある範囲が半年しかなく通年を収録できなかった。
  **「この範囲の外は展開しない」(AGENTS.md) は、規則が書けるかではなく、
  ソースがその期間を裏付けるかで決まる。**

**第三者商用アプリ (ごみスケ・さんあ〜る等) が配信するデータは一次ソースとして採用しない** (方針 2026-07-18)。
技術的に取得できても、約款不明の商用インフラへの依存・導入形態による挙動差 (さいたま=Web埋め込みで取得可 /
千代田=アプリのみで不可)・商用データベース複製の法務リスクがある。該当自治体は市の直接公開物を探すか、
市への照会 (オープンデータ化要望) で対応する。

**ソースが機械可読でない・地区割に確信が持てないなら、作らずに調査報告で止める** (推測でデータを作らない)。

## 2. 実装 (tools/_lib を使う)

`tools/_template/` を `tools/<形式>-extractor/<handle>/` にコピーして埋める。
共通部品 (`tools/_lib/`) にあるものを再実装しない — 一覧は `AGENTS.md`「共通部品」の表を見る。
実日付から weekly / monthly_specific の規則を導くときの `classify.mjs`、
ABR 町字マスターを引く `abr.mjs` も含めてそこが正典。

規約:
- 「第n」は全都市「その月 n 回目の該当曜日」(第n週ではない)。頻度が季節変動する品目 (調布のペット等) は
  weekly にせず monthly_specific (実日付列挙) で。
- 同日収集グループは days 配列を共有 (YAML anchor になり同日性が明示される)。
- 政令市はコース slug を `<区romaji>-<n>`、区またぎ同名町は「町名（区名）」(川崎先例)。
- taxonomy.yaml は `schema/categories.yaml` の部分集合 + ラベル override。**新語彙が要りそうなら追加せず相談**。
- 未パース表記は throw (黙って落とさない)。`Date.now()` 禁止 (EXTRACTED_AT を env で)。
- **表の外にある情報を読む**。可燃の休止日・区単位の例外は「※注意」に実日付で書かれていることがある
  (日高)。曜日や他コースの観測から推測しない。
- **`monthly_specific` は休業を復元できない**。実日付列挙では休業日がリストから抜けるだけなので
  「休んだ」と「元々収集がない」が区別できなくなる。休みは cancelled override で明示する
  (経緯は `tools/_lib/classify.mjs` の冒頭)。
- **1 カテゴリに複数規則が要ることがある** (飯能の粗大 = 月曜3回目 ∪ 水曜1回目)。曜日ごとに分ける。
  1 本にまとめると `days × occurrences` の直積に広がって別の日が生える。

踏みやすい罠 (詳細は各 extractor の README):

| 罠 | 対処 | 実例 |
|---|---|---|
| 近い色を取り違える | 閾値で「どれかに当たるか」を見ず、**最も近い参照色 1 つに割り当てる** | 飯能の不燃(255,245,64) と びん(251,201,75) は \|RGB差\| で 59 しか離れていない |
| セルの高さ・結合 | 最終行が上下 2 段に割れる/割れないが月と列で変わる。罫線を信じ、暦の週数と突き合わせる | 飯能 (24 日ぶん取りこぼした) |
| 余分な行を拾う | 週行の高さを実測して狭く選別する | 飯能 (次ブロックの見出し枠 39.9pt を週行 42.5pt と誤認) |

**下流 (city.tecoli) に効くもの** — 変えるときは事前に連絡する:

- ファイル名は `writeCourses` が `course-${metadata.course}.yaml` で決める。改名は下流のビルドを壊しうる
  (飯能で ics-builder のファイル名決め打ちに当たった)。
- **`metadata.course` の値は下流の識別子**。表示・URL・ics の slug に使われる。値そのものを変えない。
- 出典 URL のフィールドは `source_url` (旧 `pdf_url` も schema にあるが新規は `source_url`)。
- **規則の `note` は下流に表示されるとは限らない** (2026-08-15 時点の city.tecoli は区域と例外日の note しか
  出していない)。区単位の例外 (日高の「下鹿山区は古紙・古布を市では収集しない」) は現行スキーマでは
  規則の note に逃がすしかないが、**それだけでは利用者に届かない**ことを承知しておく。

> 実行環境の注: この環境の既定 `python3` (pyenv 3.13.15) には pdfplumber / numpy / PIL が入っていない。
> 入っているのは 3.10.2 の方。PDF 系 extractor を回すときは PATH を通す。

### areas の作り方 (2026-07-23 確立。岡山・倉敷が完成形の見本)

下流 (city.tecoli) は利用者の**居住町名の特定**に areas を使う。次の規約で作る:

- **1 area = 1 町名 (丁目単位)**。ソースが地名列挙の塊でも分解する (倉敷の教訓)。
  構造は `{name, yomi?, machiaza_id?, note?}` (schema は name のみ必須)。
- **yomi**: ①デジタル庁 ABR 町字マスター (`data.address-br.digital.go.jp/mt_town/pref/mt_town_pref<NN>.csv.zip`、
  政府標準利用規約。DCAT フィード `/api/feed/dcat-ap/2.1.1.json` で全 URL が引ける) のカナをひらがな化。
  ベース町名 (丁目・注記・記号サフィクス除去) で照合。② ABR に無ければ一次資料自身の読み括弧
  「地名（ひらがな）」(市公式ルビ。倉敷の宇頭間（うとうま）等)。③ひらがな/カタカナのみの町名は表記=読み。
  **どれにも無ければ付けない — 推測カナ禁止** (町内会・団地級は無いのが普通)。
  ABR が広域大字を持たない都市 (横浜の戸塚町・和泉町 等) は日本郵便 ken_all を第2ソースに併用する
  (手動配置運用。README「areas の読み・町字ID ソース」参照)。
- **machiaza_id**: ABR 町字ID を `lg_code-machiaza_id` (6桁-7桁) で。丁目まで照合 (丁目ごとに別ID。
  区またぎ丁目・区注記つき同名町も解決できる)。ABR は同一町字の重複行があるので ID で uniq してから判定。
  **区またぎ同名で一意化できなければ付けない** (岡山の西市・祇園。下流で「候補提示→利用者確定」になる)。
- **note**: 地理的区別子 (「砂川以東」「N番地〜M番地」) と限定条件 (「※一部地域のみ曜日が異なる」) のみ。
  呼びかけ・案内文 (「〜ご確認ください」「朝7時30分までに…」「〜ため注意」) は機械除去する
  (実装例: tools/api-extractor/okayama/build.mjs の stripTimeNote)。原文はキャッシュに残す。
- **割れ町** (同一町名が複数の日程を持つ) は note の判別子を name に昇格し「町名（判別子）」とする —
  name 単独で地域特定できるように (横浜「上郷町1〜199の一部」先例)。判別キーは記号・区注記を除いた
  ベース名 (福田①/② も同グループ)。昇格行の note は外す。判別 note の無い割れは警告を出す
  (係り先ミスの検出器になる — 倉敷の茶屋町で実証)。
- **同名の別地名** (倉敷の黒崎=中庄/玉島) は name 原文のまま。管区・コース文脈と machiaza_id で区別する。
- **同日一括の括り名** (「資源ごみ」「資源化物」等) は taxonomy の `groups` に参考情報として記録する。
  セマンティクスは「コースごとに members の規則完全一致で適用判定」(個別日程の物件・別体系地区では自然に非適用)。

## 3. 照合 (docs/opendata-sources.md「検証の考え方」に従う)

- 独立ソースがあれば `schedule.mjs` の `expandRange` + `verify.mjs` の `diffRange` で機械照合。日付レベル > 曜日レベル。
- **高コスト照合 (目視転記など) は全数をやらない**: 目標上限 p* を決め n≈3/p* 件 (5%なら60件) を
  層化サンプリング (`sampleStratified` + 例外的な行を追加) → ゼロ不一致で打ち切り。不一致 1 件で昇格。
- 不一致はベイズ的に裁定 (印刷物側の誤植事前確率が高い。同パターン隣接町・他表と突き合わせ)、
  判断根拠を notes に書く。**ソースを勝手に「修正」しない**。
- meta.yaml notes に「確率的信頼度:」1 行 (N=独立誤り単位のパターン/行数、rule of three 上限、残余リスク、等級)。
- **「不一致 0」を報告する前に、検査が効くことを確かめる。** 抽出か生成物を 1 日ぶん書き換えて回し、
  差分が出ることを見る。出なければその検査は検査になっていない
  (飯能では最初の改竄テストが、生成物に存在しない日付を狙って空振りしていた)。

## 4. 仕上げ

1. `municipalities/<県>/<handle>/` の meta.yaml (source 3 URL + notes: 運用ルール・年末年始・検証・確率的信頼度)
2. `make test` を通す (schema+語彙+整合、extractor 静的検査、ESLint、単体テスト)
3. **`make regen HANDLE=<handle>` で差分ゼロを確認する** — 生成物が再現できることの証明。
   ここを通していない自治体は、後から誤りが入っても機械が検出できない (`docs/playbook.md` §6)
4. **README の収録リストと `docs/opendata-sources.md` に追記する** (新規収録のとき)。
   既存収録の再構築なら README には既に載っている
5. 一次ソースのスナップショットは **テキスト / CSV 由来のときだけ** `docs/sources/<handle>_…_<日付>` へ置く。
   HTML / PDF 由来は置かない慣行になっている (2026-08-19 時点で 34 収録中 4 件のみ。
   いずれも chofu / iruma / suginami / tokyo-nakano で、fetch から再取得できるものは残していない)

## 5. エージェント並行運用 (統括者向け)

2026-07-17 に 3 自治体 (杉並・川崎・調布) を 1 日で収録した実証済みモデル:

- **1 自治体 1 エージェント**。書き込み許可は `tools/*/<handle>/` と `municipalities/<県>/<handle>/` のみ。
  docs/・schema/・他自治体・git 操作は禁止 (統合担当が一元処理)。
- 指示に含める確定事項: handle (レジストリで引いた値)、**survey.yaml の参照** (一次ソース・罠が集約済み)、
  カテゴリ対応の当たり、運用ルール、本プレイブックと手本自治体の参照。
- 統合担当はレビューで **報告を鵜呑みにせず追試** する: verify 再実行、抜き取りで一次ソースを直接見る、
  build 再現、npm test。その後 docs 統合 → ics 生成 → 自治体単位で commit。
- 貢献者 1 人が単独で回すときの進行管理 (停止点・承認する 4 項目・撤退条件) は
  `.claude/skills/add-municipality/SKILL.md` にある。本節は統括者が複数を並行させるときの話。

## 6. 既存収録の再構築 (生成器が無い自治体)

**データはあるが生成器が無い自治体がある。** `scripts/check-regen.mjs` は生成器の無い自治体を
skip するので、**その間は誤りが機械に検出されない**。飯能は 4 か月ぶん誤った収集日を配信していた
(第 5 週の読み違い。人が PDF を見るまで誰も気づかなかった)。

**対象の一覧は `make regen` の skip 行が正典。** ディレクトリ名の突き合わせでは誤検出する
(kamifurano-town は生成器が実在し「build.mjs 規約に乗っていない」だけ)。

```
$ make regen
- hidaka: 生成器が無い (データは手書き) — skip
```

### 新規収録と違うところ

**既存データが照合の基準になる**ので、順序が変わる。

1. 一次ソースを取り、§1 の判定で方式を決める
2. `extract` を書く — **ここで止めて既存データと全日付照合する**。build はまだ書かない
3. 差分を一次ソースで裁定する (下記)
4. 差分ゼロになってから `build` を書き、生成物を正典に切り替える
5. `make regen HANDLE=<handle>` で差分ゼロを確認

### 差分が出たときの裁定

**どちらが誤っているかは一次ソースを見て決める。** 該当箇所を画像化して目視する。

- **既存データが誤っていた** (飯能) — 配信済みの誤りなので、**まずデータを直してコミットし、下流に連絡する**。
  extractor の作業はその後。修正前のデータに対して照合を回すと差分が出ることを確認すると、
  検査が効いていることの裏づけになる (飯能ではちょうど 7 日 = 手で直した 7 日と一致した)
- **既存データが正しかった** (日高) — それ自体が成果。20 コース × 365 日 = 7300 日枠で不一致 0 だった。
  ヘッダが「人間による目視レビューは未実施」と断っていたものに、機械で裏づけが取れた

### 既存データの記述を信じない

- **ヘッダの `Auto-generated by ...` は当てにならない。** 飯能・日高とも、名指しされた生成器は存在しなかった
- **ヘッダのメモ・凡例を引き継がない。** 飯能の色凡例 (灰=不燃・紫=粗大・白=紙布) は実物と違っていた。
  読み違えた側が書いた記述なので、**実データから測り直す**
- **表現を変える必要があるかは別問題。** 日高の資源 7 品目は `monthly_specific` が正しい
  (季節で増便・隔月・年 4 回があり月内 n 回目では表せない)。「規則に畳めるほうが良い」ではない
